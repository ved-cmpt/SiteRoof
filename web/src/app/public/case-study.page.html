SiteRoof: coordinating site work, decisions and progress

How a small modular monolith handles the parts of construction software that are easy to get wrong: who may see and change what, approvals that happen exactly once, an unreliable downstream ERP, and dashboards that are always derived from the records.

The problem

On a commercial renovation, the schedule lives in the office and the facts live on site. A drywall crew discovers it is 40 sheets short; the supervisor texts the project manager; the request is approved in an email thread; purchasing may or may not hear about it. Meanwhile the "percent complete" in the weekly report was typed in by hand.

SiteRoof is a deliberately scoped execution tool for that gap: projects, milestones, assigned work orders, field progress with supervisor verification, and a limited material approval flow that hands off to an ERP. It is not a purchasing suite, document control system or scheduling engine.

Who it is for

Project manager

Creates projects and milestones, approves or rejects material requests, watches overdue work and the approval backlog.

Site supervisor

Creates and assigns work orders to people on the roster, verifies progress, resolves blockers and closes out work.

Crew member

Sees assigned work on their projects only, reports quantities, notes and blockers, requests materials.

Admin

Manages workspace settings and people; can read every project in the workspace.

Business rules the code enforces

  • Every work order belongs to a project, and can only be assigned to a member of that project's roster.
  • Quantities can't be negative (validated in the API and by CHECK constraints in SQL Server).
  • Work-order status follows a state machine: Open → In progress ⇄ Blocked → Completed → Closed, with cancel and reopen. Completing requires all finish-to-start dependencies to be done; closing requires verified progress, no open blockers and no pending material requests.
  • Closed and cancelled work is locked. Editing it returns 409 work-order-locked; only a project manager can reopen closed work, with a reason that is audited.
  • Progress must be verified by someone other than the person who reported it.
  • A material request is submitted once (client-generated idempotency key) and decided once by the project manager. Repeating the same decision is a no-op; contradicting it is a 409.
  • Concurrent edits use SQL Server rowversion. A stale version returns 409 concurrency-conflict and the UI shows a "someone else changed this" banner instead of overwriting.
  • Dependencies stay inside one project and can't form cycles.

Architecture

One deployable: the ASP.NET Core API serves the compiled Angular app from the same origin, which keeps cookie authentication simple (no CORS, no tokens in browser storage) and fits a single free container. Inside, the code is organised by feature module (projects, work orders, materials, integrations, dashboards, demo) with services that own authorization, validation and transactions.

Data model

Business tables carry a TenantId (directly or through their project) with EF Core global query filters, so a forgotten check fails closed. Two documented T-SQL views feed the dashboards: vw_ProjectWorkOrderRollup (one conditional-aggregation pass per project, supported by the (ProjectId, Status, DueDate) index) and vw_WorkPackageCompletion (per-package completion using OUTER APPLY over progress logs).

ERP integration: transactional outbox

  1. The manager approves. In one SaveChanges (one database transaction) SiteRoof updates the request, writes the audit event and inserts an outbox row keyed mr-approved:{id}.
  2. A background worker claims due rows with UPDATE … OUTPUT using READPAST, UPDLOCK, so concurrent workers never deliver the same row at once.
  3. It POSTs the requisition to the self-hosted mock ERP with an Idempotency-Key header. In the demo, the ERP answers the first attempt with 503.
  4. Transient failures are rescheduled with exponential backoff (5 s, 10 s, 20 s, 40 s, capped) for at most five attempts, then dead-lettered as Failed with a manual retry.
  5. On success the external reference is stored on the request; the ERP keeps one requisition per key, so a redelivery returns the same reference instead of a duplicate.

Why this stack

  • Angular + TypeScript (strict) + Angular Material: typed forms, standalone components and signals; accessible components out of the box for internal business apps.
  • ASP.NET Core + C#: dependency injection, model validation, ProblemDetails, built-in rate limiting, Identity and antiforgery — the enterprise defaults without extra frameworks.
  • SQL Server + EF Core: relational integrity where it matters (FKs, unique keys, CHECK constraints, rowversion) plus hand-written T-SQL where it is clearer (views, the outbox claim).
  • xUnit + Testcontainers + Playwright: business rules are tested against a real SQL Server and through a real browser, not mocks.
  • Modular monolith: one deployable keeps the demo free to host; feature boundaries keep it easy to split later if the ERP adapter ever needed its own service.

Security decisions

  • Cookie authentication (HttpOnly, SameSite=Lax, Secure when hosted) and antiforgery tokens validated on every unsafe /api request.
  • Object-level authorization in the service layer: other tenants' ids return 404; same-tenant projects without membership return 403. The UI hides actions only as a convenience.
  • Guest isolation: each "Try Demo" click provisions a separate tenant with password-less personas. No shared mutable data, no credentials shown anywhere.
  • Rate limits per client (global API, demo provisioning, sign-in), demo quotas, capacity cap and automatic expiry.
  • Security headers (CSP without inline scripts, frame-ancestors none, nosniff, referrer policy), structured JSON logs, secrets only from environment variables.

Testing

Backend integration tests boot the real API (middleware, auth, CSRF, EF Core) against SQL Server 2022 in a disposable Testcontainers container. Each test provisions its own demo tenant, so tests never reset each other's data. They cover the must-pass rules: URL tampering by a crew member, cross-tenant ids, approvals that are logged, idempotent and forbidden for crew, ERP 503-then-retry without duplicates, bounded retries, 409 on conflicting edits, and dashboard/database/activity updates when work is created and completed. Angular unit tests cover services and components; Playwright runs the recruiter scenario end to end in Chromium.

Exact commands and the latest recorded results are kept in docs/STATUS.md. No performance or uptime figures are claimed because none have been measured on a hosted environment.

Deployment

Demo walkthrough

  1. Open Riverbend. As Marcus (site supervisor), open Riverbend Library Renovation and turn on "Overdue only": the drywall work orders are late and RBL-007 is blocked by a 40-sheet shortage.
  2. Submit progress. Switch to Leah (crew). On RBL-006 report the square metres installed today. Her view only contains Riverbend.
  3. Verify. Switch back to Marcus and verify Leah's log.
  4. Approve materials. As Dana (project manager), open Approvals and approve the Type X board for RBL-007.
  5. Watch the ERP. The requisition shows "Retrying" after the simulated 503, then "Acknowledged by ERP" with a reference number.
  6. Check the dashboard. Overview and the project dashboard recalculate from the database: approval backlog down by one, progress up.

Known limitations

  • Not yet deployed; hosting steps are documented for the owner.
  • Single region, single container. Data-protection keys are not persisted, so a container restart signs visitors out (demo workspaces are disposable anyway).
  • No offline mode, file attachments, notifications or scheduling engine; those belong to other tools.
  • The ERP is a self-hosted simulator, not a real purchasing system.
  • The blocker summary is rules-based keyword classification. An optional AI provider interface exists but is disabled and not implemented.
